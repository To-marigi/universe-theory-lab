## 1. 結論

根本設計は、全 544 generators を一括 materialize してから解く方式から、root-bound な stage plan、stage-specific materialization、content-addressed attempt、fail-closed supervisor/campaign/worker へ置き換えられた。最新の marker smoke `M1` は stage 1 を worker 開始から `6.947389209999528` 秒で materialize し、`6.951342402004229` 秒で完了した。sampled container peak memory は `195978854` bytes だった。旧方式の約 `141.9` 秒、約 `4 GiB RSS`、`12,672,299` loaded terms に対し、新方式は stage 1 の `1,569` loaded terms だけを扱う。M1 は `attempt.json.identity.execution_policy.runtime_binding_schema=sr2v-runtime-binding-v1` と完全な source bindings を fingerprint に含めた最初の固定済み marker である。

ただし、これは異なる計算範囲の比較であり、full solver が高速化されたという証明ではない。実際、stage 7 は native、incremental、direct `system("sat")` のすべてで最初の chart saturation を完了できず、stage 8 は chart-first と torus-first の双方で timeout した。stage 1、2、4、6 の完了結果、および direct A/B の stage 1、4 の結果はいずれも unit ideal ではない。

QQ redundancy audit は raw generators に 3 本の厳密な冗長関係を証明した。一方、既存の native 計算では N1/N2 と N4/N6 が既に同じ最終 basis を返しており、冗長行削除による saturation 高速化は実測されていない。direct A/B route は stage 1 と 4 で全 16 factors の exact equivalence と exponent certificate を検証したが、direct system route の stage 7 は同じ chart bottleneck で timeout した。

したがって本 pilot の確定成果は、低コスト stage の再現可能な計算、冗長関係と saturation 実装の exact audit、timeout を含む durable evidence、そして異常終了後も canonical result を残す監督基盤である。unit ideal、full QQ/lift、resource-open のいずれも確定していない。

### Supervisor

- canonical JSON envelope、root/budget/source binding、timestamp 非依存の attempt fingerprint を検証する。
- fingerprint ごとの immutable attempt directory、atomic JSON write、LF hash-chain event log、terminal status mapping を管理する。
- malformed/incomplete/unsafe history、同一 fingerprint の timeout retry、aggregate wall budget 超過を fail-closed で拒否する。
- source snapshot と terminal event/result の整合、event log、worker protocol、cleanup、host process termination、postflight、container contract を検証する。
- `sr2v-runtime-binding-v1` marker では全 source bindings と source snapshot の一致を必須にし、success/nonterminal result の container contract、host termination、postflight、zero survivors、terminal event/result bindings を history load 時にも再検証する。

### Stage plan

- frozen root/chunks/indices に結合した arena metadata を読み、zero/duplicate rows を除外する。
- generator term cost 順に deterministic nested prefixes を作り、stage semantic digest と selected-row digest を固定する。
- chart/localizer、bottom factors、torus factor の metadata と、root semantic digest の不一致を拒否する。

### Worker

- request、root、全 chunk digest を認証する一方、JSON decode と polynomial construction は stage に必要な records に限定する。
- 53 変数 `t1..t4,s0..s47,h` の環を使い、Rabinowitsch 変数 `z` を導入しない。
- `RLIMIT_AS=8 GiB`、`max_loaded_terms=5,000,000`、`max_live_basis_terms=5,000,000` を適用し、`ru_maxrss`、`ru_stime`、`ru_utime` を記録する。
- `build_only`、native sequential saturation、incremental native、redundancy audit、direct A/B saturation、direct system saturation を別 method として fingerprint に含める。
- direct libSingular route は polynomial sequence を保持し、`isSB` で standard basis を再計算しない。A/B route は `sat_with_exp` と kernel `system("sat")` を双方向 basis reduction で比較し、exponent certificate を検証する。

### Campaign と compose

- campaign file lock により同一 campaign の同時実行を防ぎ、120 秒の finalization reserve を保持する。
- preflight/postflight で stale solver container と legacy `sage-eval` process を監査する。
- Docker stats の memory/CPU/PIDs と container process table を定期取得し、soft-memory、timeout、異常終了を監視する。
- stdout/stderr を継続 drain し、worker が短時間で正常終了した場合も container state probe と競合させない。
- image digest、8 GiB memory+swap、PIDs 256、network none、restart no、read-only repository mount を検証する。
- compose は Sage 10.9、`OMP_NUM_THREADS=1`、`OPENBLAS_NUM_THREADS=1`、`shm_size=2g`、`init=true` を固定する。
- 成功以外でも cleanup、host termination、postflight を実行し、terminal result を必ず確定する。

## 7. 運用失敗 O1 と修正の検証

O1 は成功ではない。worker result は `null`、status は `ERROR_SUPERVISOR_EXCEPTION` であり、event seq 15 に次の分類根拠が残る。

`container process audit failed: ... container ... is not running`

短時間で正常終了した worker に対し、campaign の process audit が container 停止と競合し、正常終了を supervisor exception と誤分類した。これを通常の worker exit として無条件に成功扱いせず、campaign の probe/drain/termination 処理を修正した。`_container_stopped_during_probe` により probe 中の停止を識別し、stdout/stderr の drain、container state、worker protocol を合わせて terminal classification を行う。

修正後の B1-R は同じ request payload digest `c661e1f05e98bf940216b04e154279554101b2fc5b458b22777c608bfa244153` を別 source-bound fingerprint で実行し、`BUILD_COMPLETED`、worker finish `6.890686523998738` 秒、cleanup verified を得た。さらに C1 contract smoke は次をすべて確認した。

- `container_contract_verified=true`
- `event_log_valid=true`
- `host_process_termination_verified=true`
- `postflight_audit_verified=true`
- `cleanup_verified=true`
- `process_returncode=0`
- postflight stale containers 0、legacy processes 0
- request protocol verified、worker result count 1

この時系列により、O1 は durable operational failure として保存され、その race の修正は B1-R と C1 の二段階で回帰確認された。M1 は同じ build-only request payload `22ac4d242bf584b399f9d61fd0dfbe3d56579561a2cdf4a7b2295e38a7bec58e` を enhanced runtime binding で再度 smoke し、`container_contract_verified=true`、`host_process_termination_verified=true`、`postflight_audit_verified=true`、`cleanup_verified=true`、zero postflight survivors を確認した。これは solver の追加数学結果ではなく、最新 runtime marker の運用契約検証である。

## 8. generator redundancy audit

R-GF は modulus `32003` で 3 relation を検出し、共通 multiplier は `q=32002`、relation set SHA-256 は `885f6b3c84d0600b04b218051345c326522a37a66ea618ee9fbd43da88013435` だった。

R-QQ は同じ 3 relation を厳密 QQ arithmetic で再検証した。共通 multiplier は `q=-1`、canonical relation pairs は次のとおりである。

| relation pair | relation SHA-256 |

| `(8,[1,2]) -> (9,[6,7])` | `b18452500dec63d53c4214ebe5ab985c1442b70e03a033ebd35c9ca538fe4bdf` |
