これらから、「最大生成元だけが原因」「48個の torus 変数の積だけが原因」「localizer だけが唯一の原因」のいずれも支持されない。表現、変数、消去順序、localizer、生成元間の相互作用が複合した問題と判断する。

## 4. 現行実装の P0 欠陥

P0 は、計算方式の優劣を比較する前に是正すべき、安全性・終了意味・再現性の欠陥とする。

### P0-1. 失敗が shell 成功に見える

チャートが `TIMEOUT` または `ERROR` でも、現行 main は最終的に exit code 0 を返す。これは CI、ラッパー、人間のいずれに対しても失敗を隠す。

必要な変更:

- `TIMEOUT`、`ERROR`、kill 未確認、結果欠落を非 0 終了にする
- チャートごとの machine-readable result を次の実行前に fsync 相当で耐久化する
- 結果の集約器は、失敗チャートを成功に変換しない

### P0-2. worker 残留時の fail-closed が不十分

timeout 後の worker 終了を確認できない場合、次の worker を起動してはならない。過去にはコンテナ内の実プロセス名が `sage-eval` であることを見落とし、約 6.6 GiB のプロセスを長時間残した実害がある。

必要な変更:

- 開始前と終了後の両方で、対象 worker と Singular 子プロセスの生存を確認する
- TERM → bounded wait → KILL の後、0 survivor を確認する
- 1つでも survivor がいれば campaign 全体を即時中止する
- 実行中は常に 1 worker とする

### P0-3. 契約上の resource budget が supervisor で完結していない

現行実装は per-chart hard timeout と一部の RLIMIT に依存し、次の契約を一貫して強制していない。

- aggregate 43,200 秒
- soft RSS 7.0/7.5 GiB
- hard memory 8 GiB
- live terms 5,000,000
- split depth 6 / 64

少なくとも PID、RSS、CPU time、wall time、実行 stage、完了項目数を 15〜30 秒間隔で記録し、soft stop、hard stop、終了理由を分離する。CAS 内部の live terms を直接取得できない場合は、未監視のまま強制済みと記録せず、取得不能と代替指標を明記する。

### P0-4. 終端判定と独立検証が未分離

GF(p) での `[1]` は scout の進展にすぎない。さらに QQ 上で `[1]` が得られても、それだけで独立な証明書とはしない。

必要な終端パス:

1. QQ 上で対象 ideal が unit ideal であることを exact に計算する。
2. 入力生成元から `1` または局所化に対応する冪への lift 係数を取得する。
3. 別パスで係数身元、入力 digest、等式を exact に再検算する。
4. 検証成功後にのみ terminal certificate とする。

### P0-5. 実 CAS を含む運用テストが不足

現行テストは source-level 契約と Sage を呼ばない合成テストが中心である。次を小さい人工 ideal で実際に実行する integration test が必要である。

- 正常完了
- timeout と非 0 終了
- worker および子プロセスの kill 確認
- progress/result の耐久化
- 実行引数が `sage -c` のコードに誤結合されないこと

## 5. 現行実装の P1 欠陥

P1 は、P0 安全化後の pilot が実際に比較可能になるための、表現・マテリアライズ・計算方式の欠陥とする。

### P1-1. subset escalation 前に全生成元を構築している

現行 worker は必要 chunk を読み、544生成元を全て多項式オブジェクトにした後で、16/32/64/… の stage に入る。したがって現行の subset escalation は「大きな生成元を構築しない」最適化にはなっていない。

必要な変更は stage-specific materialization である。最初は chunk 索引、generator recipe、term-count 等のメタデータだけを読み、各 stage で必要な生成元だけを materialize する。stage 開始前に予測 term budget を超える場合は CAS を起動しない。

### P1-2. stage 間で計算を再利用しない

現行の各 subset stage は `ideal(...).groebner_basis()` を新規に呼び、前 stage の中間結果を捨てる。これにより stage を増やすたびに前処理と reduction を再実行する。

新方式が incremental 基底の exact 再利用を安全に提供できない場合、subset 数を細かく増やすこと自体を見直す。「stage が進むこと」と「全体の計算量が減ること」を混同しない。

### P1-3. 計算バックエンドと monomial order が固定

現行は `degrevlex` の単一路線である。`std`、`slimgb` 等の利用可能バックエンド、変数順序、block/order 設計は、凍結入力と同一 budget の bounded pilot として比較する。ただし、order 変更だけを現行54変数の long run で試さない。

### P1-4. 局所化後の正規化が不足

現行の重複除去は polynomial-ID tuple の完全一致が中心である。上半分の torus monomial、安全に証明済みの係数単元、チャート上で可逆な共通因子による unit-associate を、証明可能な範囲で正規化してから CAS へ渡す余地がある。

正規化は、局所化していない因子を誤って捨てないよう fail-closed に実装する。

### P1-5. 現行 Rabinowitsch 形式への固定

`1-zL` は exact だが、追加変数 `z` と高次数 localizer `L` を同時に渡す。U2 では最小 subset でも停滞しているため、同じ形式の long run を追加する根拠はない。

## 6. 採用する実行順序

次の順序を固定する。前段の exit criteria を満たさない限り、後段の重い計算へ進まない。

### Stage 0. 安全な supervisor

exit criteria:

- timeout、error、kill 失敗がそれぞれ非 0 終了になる
- pre/post process audit と 0 survivor 確認が自動テストされる
- per-chart と aggregate の budget が両方強制される
- 一定間隔の progress と resource telemetry が耐久化される
- 途中終了後に、終了理由と最後の完了地点を機械可読に復元できる

### Stage 1. stage-specific materialization

exit criteria:

- 全生成元を事前構築せず、対象 stage のみを materialize する
- input source、chunk digest、generator order、選択行、localization factors を request に固定する
- 構築前見積もりと構築後実測の terms/RSS を記録する
- 人工 ideal と小型の実入力で、stage 間の選択と終了意味を exact に検証する

### Stage 2. 新方式の U2 bounded pilot

U2 / GF(32003) の凍結入力を使い、1 worker で短時間の比較を行う。各 pilot に同一の input digest、generator order、時間・メモリ上限、telemetry 方式を与える。

優先する候補:

1. native saturation
2. determinantal alternative の反例駆動部分集合
3. 上記の表現に対する少数の backend/order 比較

native saturation では、torus 因子だけでなく `F_lambda` と対象 chart 因子を含む、元の局所化と同値な全因子を扱う。Sage 10.9 の native saturation は保存済み F4SAT 論文の実装そのものではないため、論文の速度をそのまま前提にしない。

determinantal alternative では、全 2×2 minors を一括生成しない。反例と exact witness に基づいて entries/minors を追加し、部分集合による証明が全体に対して安全な十分条件になる場合だけ利用する。

pilot の選定指標は「最初の進捗が早い」ではなく、次の全てを含む。

- 同じ bounded budget 内の進捗
- peak RSS と増加傾向
- 中間結果の耐久化可能性
- QQ への移行可能性
- 独立検証可能な lift/certificate の取得可能性

GF(p) の結果は方法選定の scout に限定する。GF(p) で `[1]` が得られても、project の exact claim や terminal result に格上げしない。

### Stage 3. QQ exact run と lift

Stage 2 で選定された方式だけを QQ 上に移す。まず小型の exact 入力で lift の取得と独立検証パスを試験し、検証不能なバックエンドを full QQ run に使わない。

QQ 計算の終了だけでなく、入力 digest に紐付く lift の exact 再検算が成功して初めて証明完了とする。

## 7. aligned 52 → 49 変数削減の decision gate

aligned chart については、凍結済み audit が exponent-difference matrix の rank 3、Smith invariant factors `[1,1,1]`、primitive を証明しており、52 → 49 変数削減は有望である。

ただし、今回の blocker を計測している U2 はこの aligned 削減の適用対象ではない。U2 pilot の先行条件として aligned 削減を実装しても、現在の U2 停滞は直接改善しない。

また、削減を正式に取り込むには、unimodular forward/inverse map、指数の往復、点評価の往復を exact に検証し、影響する self-binding artifact を再凍結・再検証する必要がある。compiler / bundle / `uv.lock` 等の binding 対象への変更は、過去実測で再生成約 46 分と再検証約 46 分のコストを生じる。

したがって、aligned 52 → 49 は今回の U2 bounded pilot の後に decision gate を設ける。gate では、以下を同時に判断する。

- aligned chart が次の証明 blocker になるか
- 3変数削減の期待利得が再凍結コストを上回るか
- forward/inverse round-trip と pointwise equivalence の独立検証を完結できるか
- binding 対象の変更を1回の計画的なコミットにまとめられるか

この gate を通過するまで、aligned 削減を実装済み、高速化済み、または U2 への解決策と記述しない。

## 9. resource-open の位置づけ

選択肢4の resource-open は、敗北、中断、または証明不能の言い換えではない。問題と計算契約を固定し、実測で到達した境界と未解決 leaf を再利用可能にする、プロジェク方針に沿った正当な成果である。

ただし、正式な resource-open には少なくとも次が必要である。

- 完全な request と input/source digest
- generator order と実行 stage
- 時刻付き progress ledger
- peak RSS、CPU time、wall time
- soft/hard stop の発動理由
- worker と子プロセスの 0 survivor 確認
- どの exact claim が確定し、どの claim が未解決かの分離
- 実行済み候補と、未実行候補の分離
- 再開条件と、同じ高コスト実験を繰り返さないための禁止事項

Stage 0〜2 の bounded 検証で契約内の証明経路を選定できない場合、上記を満たす resource-open leaf を正式な終端成果とする。「長時間待てば終わるはず」という未検証の期待は、resource-open を遅らせる理由にしない。
